# ソフトウェアテスト仕様書兼結果書 記述形式

## 1. 単体テスト仕様書兼結果書

### 1.1 テスト項目テンプレート

```markdown
## テスト項目 UT-XXX: [テスト項目名]

### 基本情報
- **テストID**: UT-XXX
- **テスト対象**: [関数名/モジュール名]
- **テスト分類**: [正常系/異常系/境界値]
- **実施者**: [実施者名]
- **実施日**: [YYYY-MM-DD]

### テスト内容
- **テスト目的**: [テストの目的]
- **前提条件**: [テスト実行前の条件]
- **テストデータ**: [入力データ]
- **実行手順**: 
  1. [手順1]
  2. [手順2]
  3. [手順3]

### 期待結果
- **期待値**: [期待される結果]
- **期待動作**: [期待される動作]

### 実行結果
- **実測値**: [実際の結果]
- **実際動作**: [実際の動作]
- **判定**: ✅ 合格 / ❌ 不合格
- **備考**: [特記事項]

### 不具合情報（不合格の場合）
- **不具合ID**: BUG-XXX
- **不具合内容**: [不具合の詳細]
- **修正内容**: [修正した内容]
- **再テスト結果**: [再テスト後の結果]
```

### 1.2 単体テスト実行例

```markdown
## テスト項目 UT-001: 商品検索API正常動作テスト

### 基本情報
- **テストID**: UT-001
- **テスト対象**: GET /api/products
- **テスト分類**: 正常系
- **実施者**: 開発者A
- **実施日**: 2024-01-15

### テスト内容
- **テスト目的**: 商品検索APIが正常に動作することを確認
- **前提条件**: 
  - サーバーが起動している
  - データベースに商品データが存在する
- **テストデータ**: 
  - クエリパラメータ: q=りんご
- **実行手順**:
  1. サーバーを起動する
  2. GET /api/products?q=りんご にリクエストを送信
  3. レスポンスを確認する

### 期待結果
- **期待値**: 
  - ステータスコード: 200
  - レスポンス形式: JSON配列
- **期待動作**: 
  - 「りんご」を含む商品が検索される
  - 商品ID、名前、価格、在庫が返される

### 実行結果
- **実測値**: 
  - ステータスコード: 200
  - レスポンス: [{"productId":1,"name":"りんご","price":100,"stock":50}]
- **実際動作**: 期待通りの結果が返された
- **判定**: ✅ 合格
- **備考**: なし
```

### 2.2 結合テスト実行例

```markdown
## テスト項目 IT-001: 注文作成〜在庫更新連携テスト

### 基本情報
- **テストID**: IT-001
- **テスト対象**: 注文作成API → 在庫更新処理
- **テスト分類**: 機能結合
- **実施者**: 開発者B
- **実施日**: 2024-01-16

### テスト内容
- **テスト目的**: 注文作成時に在庫が正常に更新されることを確認
- **結合範囲**: 注文API、在庫管理機能、データベース
- **前提条件**: 
  - 商品ID:1の在庫が100個
  - 顧客データが存在する
- **テストシナリオ**: 商品10個の注文を作成し、在庫が90個に減ることを確認
- **テストデータ**: 
  ```json
  {
    "customerInfo": {"name": "田中太郎", "address": "東京都", "contactInfo": "090-xxxx-xxxx"},
    "items": [{"productID": 1, "quantity": 10}],
    "payment": {"method": "credit"}
  }
  ```

### 実行手順
1. 注文前の在庫を確認 (GET /api/products/1/stock)
2. 注文を作成 (POST /api/orders)
3. 注文後の在庫を確認 (GET /api/products/1/stock)
4. 注文データを確認 (GET /api/orders/{id})

### 期待結果
- **期待動作**: 
  - 注文が正常に作成される
  - 在庫が100→90に減る
  - 注文詳細が正しく記録される
- **期待データ**: 
  - 注文テーブルに1件追加
  - 在庫テーブルが更新される

### 実行結果
- **実際動作**: 期待通りの動作を確認
- **実際データ**: 
  - 在庫: 100→90 ✅
  - 注文ID: 1 (新規作成) ✅
- **判定**: ✅ 合格
- **備考**: トランザクション処理も正常

### 検証項目
- [x] データの整合性
- [x] トランザクションの完整性
- [x] エラーハンドリング
- [x] パフォーマンス
```

### 3.2 総合テスト実行例

```markdown
## テスト項目 ST-001: ECサイト完全購入フローテスト

### 基本情報
- **テストID**: ST-001
- **テスト対象**: ECサイト全体（商品検索→注文→決済→発送）
- **テスト分類**: 機能テスト
- **実施者**: テスト担当者C
- **実施日**: 2024-01-17

### テスト内容
- **テスト目的**: ユーザーが商品購入から発送完了まで正常に完了できることを確認
- **テストシナリオ**: 
  1. 商品を検索
  2. 商品を選択
  3. 顧客情報を入力
  4. 注文を確定
  5. 管理者が発送処理
- **前提条件**: 
  - フロントエンドが起動済み
  - バックエンドが起動済み
  - テスト用商品データが存在
- **テスト環境**: 
  - Frontend: http://localhost:3000
  - Backend: http://localhost:3001
- **テストデータ**: 
  - 商品: りんご (ID:1, 価格:100円, 在庫:50個)
  - 顧客: 山田花子, 大阪府, 080-xxxx-xxxx

### 実行手順
1. ブラウザでフロントエンドにアクセス
2. 検索窓に「りんご」と入力して検索
3. 検索結果からりんごを選択
4. 数量を5個に設定
5. 顧客情報を入力
6. 注文を確定
7. 管理画面で注文を確認
8. 発送状態を「発送済み」に変更
9. 在庫の減少を確認

### 期待結果
- **システム動作**: 
  - 検索結果が正しく表示される
  - 注文が正常に作成される
  - 在庫が45個に減る
  - 発送状態が更新される
- **ユーザー体験**: 
  - 直感的な操作で購入完了
  - エラーメッセージが適切に表示
- **性能要件**: 
  - 各API応答時間 < 2秒
  - 画面遷移時間 < 3秒

### 実行結果
- **実際動作**: 
  - 検索〜注文〜発送まで正常動作 ✅
  - 在庫更新も正常 ✅
- **実際体験**: 
  - 操作が直感的で分かりやすい ✅
  - エラーハンドリングも適切 ✅
- **性能実測**: 
  - API応答時間: 0.5-1.2秒 ✅
  - 画面遷移: 1-2秒 ✅
- **判定**: ✅ 合格
- **備考**: 全体的に期待通りの動作を確認

### 検証項目

- [x] 非機能要件の充足

## 5. 使用方法

1. **単体テスト**: 各APIエンドポイントの個別テスト
2. **結合テスト**: 複数のAPIやモジュール間の連携テスト
3. **総合テスト**: エンドツーエンドのシナリオテスト

各テストレベルで上記のテンプレートを使用し、実際の結果を記録してください。
